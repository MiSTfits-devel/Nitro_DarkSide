measured scope

The NTR EVA checkpoint compares frames 34, 71, 84, 87, 90, 97, 108, 116, 120 and 123 against independent direct melonDS frame dumps: both displays passed pixel-perfect. That v11 checkpoint uses recorded 3D input and checks Haskell capture writes against a separate oracle-only VRAM shadow (192 capture lines); it is not the Haskell-3D proof. The separate v12 M4 gate replays raw GX writes through the Haskell chip: 768 cartridge 3D lines and 23,808 screen lines match production, as do 6,720 directed/seeded scene lines. The 2D combined matrix has 1,897 valid lines exact and three explicit invalid-mode rejections. See clash/README.md for commands, finite feature coverage and artifact locations.

The cache now has 192 LRU slots, plans each line from its own state, and counts evaluated prefetch plus demand renders and invalidations. Immutable array and decoder-owned trace memories carry exact identities; opaque memory callbacks are never reused, and a caller composing 3D supplies a per-line 3D identity through onePassFrameWith; sprite, OBJ-window, capture and display/FIFO identities are separate key tokens. On the NTR v12 trace, 120 of 124 frames had no 3D-active lines (768 such lines were excluded and counted), and 23,040 lines were pixel-identical across OBJ, windows, mosaic, brightness and capture state: the speculative path did 14,025 renders instead of 23,040 and measured 6.85 s versus 10.81 s (1.58x) with a 100% hit rate. Those are renderer-only wall times. The final two-engine comparison instead uses independent cache/exact processes from trace-open through forced pixels, including decode, Chip replay, sprites, capture, tokens, keys, prefetch, cache maintenance, hashing and GC; exact skips cache-only tokens. It measured 36.129108 s cached versus 43.973591 s exact (1.21712x), with 29,586 total prefetch+demand renders versus 47,616. Both variants force 768 actual Haskell Chip 3D lines. Matching cross-run hash 147193483 is only a consistency check; the prior prepared-input comparison proved all 47,616 lines bitwise equal, separately from the independent production-renderer oracles.

This is one run per variant on one cartridge trace, with wall/GC noise; prefetch remains sequential, not parallel. The old unforced 3D timer is invalid and the older 1.51x figure was renderer-only, not end-to-end. The 101-check cache stress suite passes. Video mode 7 fails explicitly rather than being approximated. Commands and logs are in clash/README.md.

Those M5 figures are historical, before M6's full-region immutable-memory equality correction, not a remeasurement of the current tree. The existing M5 cache/store APIs remain. A new case in the repository's 11-case checker seeds that real cache from one palette branch, then checks independently rendered changed pixels from a different branch of the same parent; equal stream/revision labels alone cannot prove equal bytes.

The composed-chip gate is separate from this benchmark. Its free-running transaction reference checks independently queued command/parameter and geometry-event payloads, FIFO conservation and every-clock FIFO/IRQ/DMA transitions, including IF/refill priority. Overlapping RAM-count reads linearize to independent monotonic event-prefix states; undefined-busy result RAM alone is fenced. Geometry completion uses verified progress handshakes with bounded liveness, not an independent proof of exact microcycle latency. Import-time hashes and later host fixes are recorded separately in docs/GPU3D_CLASH.md; none establishes a new Quartus, generated-composed-RTL or board result.

M6 is a different execution path: the native launcher now pairs melonDS CPUs/non-GPU peripherals with authoritative Haskell GPU MMIO, memory, capture, timing and IRQ/DMA effects. Its independent v5 direct comparisons matched 200 NTR both-screen frames plus 4 MiB main RAM, and 120 actively changing real-ARM palette frames. Whole process walls, including startup/output, were 16.1 s and 4.6 s; the internal producer totals 15.91488 s/about 4.55 s are not full process timings.

A new live-cache experiment was slower (18.6 s/6.6 s whole process) and was removed completely, not retained behind an unused flag. Original M5 TARDIS is intact. Linear compositor/3D-row construction fixes remain. The real native active-input path without PNG/clock/profile diagnostics measured 40 frames in 3.582 s (about 11.2 fps), with observed touch press/drag/release input-sampling ACK latencies 67.464/191.405/128.511 ms in one same-source own-window AppKit fixture, not physical cartridge/display response measurements. The headless active scene's roughly 26 fps is not a native-GUI claim. PNG publication is now explicit opt-in, not work performed every normal display frame. No 60 fps, physical-controller press, exhaustive timing or board claim follows. Final scope and artifacts are in docs/MILESTONES.md.

The final scoped-continuation correction uses ABI2 without retiming the interpreter: only the same ARM9 handler and raw core clock whose ordinary command write actually asserted stall can append its remaining words to the existing pending FIFO. Ordinary/DMA guards remain. Timed status preserves newly asserted refill flags as well as retiring-command flags, with the standalone counter semantics unchanged. The throughput measurements above predate this narrow correction; they were not rerun.

The final ABI2 real ARM STM/SWAP regression passed with its original test/push-bit polling unchanged: all 44 RAM words stock-equal, exact nonzero POS results and one matrix push. An independent ARM7 VCOUNT64 observation proves ARM9 did not retire the next instruction during the stall. All four beats keep one scope and raw instruction clock, using ordinary/ordinary/continuation/continuation operations. This targeted proof, recorded in docs/MILESTONES.md, is separate from the prior v5 cartridge and speed measurements; M7 remains unaccepted.

The final host chip-only gate accepted all 40 default cases (16 directed, 16 seeded random, 8 fuzz), with 0 mismatches across 144,401 operations, 116,556 GX entries, 98,634 DMA triggers, 215 frames and 10,665,984 compared pixel words. These are disjoint final-checker batches; only the last fuzz case was rerun after correcting completed matrix-result visibility during a quiescent SWAP wait. The 26-operation nonzero-result regression fails twice on the old binary and passes with the fix. Exact logs and import-versus-correction provenance are in clash/README.md and docs/GPU3D_CLASH.md. This does not establish cycle-exact geometry latency or board/Quartus acceptance.

orientation

Five things that make the TARDIS frame worth trying

The idea is not "prefetch a bit harder". It is to stop treating a frame as a sequence of independent scanlines and treat it as one pass with a retroactive plan.

01 · THE COST IS LUMPY

Most lines are cheap; a few are enormous — a bank of flying enemies, a scrolling 3D scene. Budget the expensive lines, not the average line.

02 · COHERENCE IS THE ASSET

Between frames the OAM, VRAM and register bytes rarely jump. A rendered line stays exact until one of its inputs changes.

03 · LOOK AHEAD, NOT BACK

The current cache keys cover the inputs of the partial 2D line model. The future plan supplies each line's state. Full display and unified 3D inputs are not yet keyed.

04 · REPAIR, DON'T REPEAT

A mid-frame write invalidates only the lines whose key changed. Everything else is replayed, untouched.

05 · 2D AND 3D ARE ONE PICTURE

The 3D layer is not a second picture glued on afterwards. It is BG0's pixels in the same composition, at the same priority.

diagram 1 — the one-pass frame

The plan is made where the future meets the past

Scanline 0 starts the pass, not the render. The frame-start pump reads the plan the frame will produce, fills the line cache from it, and then each line either replays its cached pixels or renders and repairs.

the monad

A lens into the future, in pixel space

The TARDIS monad carries two states. The past state threads forward like ordinary state; the future state threads backward, so a reader at the start sees what the end of the computation writes. That is the whole trick: the frame-start pump can read the plan before the frame exists.

PAST · forward

getPast reads what earlier lines wrote, sendPast writes what later lines read. The line cache is the past state.

FUTURE · backward

getFuture reads what later lines write, sendFuture writes what earlier lines read. The frame plan is the future state.

RUN

runTardis ties the final future state to the initial one. The knot is the plan; the gate checks that it is consistent.

The module is Nds.Gpu2D.Tardis. It is a small reimplementation of the tardis package, with the same one-way reads and writes. The laws gate runs before anything else.

the frame

AoT plan, JIT fixup

Nds.Gpu2D.Speculate is the one-pass engine. A plan is each line's visible key and its expected pixel footprint. The prefetch pump fills the cache from that plan; a line's demand slot either replays the cached pixels or renders from the live state.

HIT

The line's key matches the plan and its rendered line is cached. Replay, no render.

MISS

No cached line. Render from the live state; fill the cache for the next frames.

FIXUP

The plan predicted a hit but a mid-frame write changed the key. Render from the live state and invalidate the stale slots.

The directed checks compare the cache against the same local renderer and exercise per-memory identity, line replacement and total render counts. They are not an independent feature oracle or a timing benchmark.

the unified GPU

3D is a layer, not a later pass

The 3D engine and the 2D engine already produce the same kind of thing: a 24-bit colour and a layer flag. In melonDS, DrawBG_3D replaces BG0's pixel with the 3D pixel and the ordinary compositor does the rest. Nds.Gpu.Unified is that same operation in one place.

ONE PIXEL TYPE

BG layers and OBJ produce LayerPixel values. The 3D layer is one more value in the same list. Priorities and blending are the ordinary composition.

ONE PASS

No second picture, no separate 3D buffer to glue. The frame is composed once in pixel space. The 3D frame is sampled as a layer.

what it is not

Scope, so a green gate is not read as more than it is

NOT A SECOND PASS

There is no second frame pass and no extra frame buffer. The speculation lives inside the one pass; a fixup is a demand line, not a replay pass.

NOT AN APPROXIMATION

A key that differs is never a tolerated miss. It invalidates and re-renders; the gate checks every pixel against the reference.

NOT ALL OF 2D YET

The trace renderer now carries sprite and OBJ-window state across phases, but whole-engine differential coverage, a Haskell capture feedback loop and full 3D integration remain outstanding.
